# Sesiones JWT de MetaGuard

La migración existente `0007_account_sessions` agrega una tabla separada por cuenta. Se conserva sin cambios y guarda únicamente SHA-256 del JWT firmado y de un token CSRF aleatorio e independiente, además de creación, vencimiento y revocación. La emisión exige una cuenta con email verificado. Los helpers reciben la llave de firma, issuer, audience, `now` UTC y vencimiento UTC desde el llamador; no eligen configuración, política de expiración ni commit/rollback. La llave debe ser un secreto criptográficamente aleatorio de al menos 256 bits (32 bytes UTF-8); el llamador confiable debe generarlo y provisionarlo. Los helpers rechazan llaves vacías, inválidas como UTF-8 o menores de 32 bytes sin registrarlas ni exponerlas.

Los JWT se firman y verifican exclusivamente con HS256. En cada validación se verifican firma, issuer, audience, formato, `iat` no futuro y `exp` todavía vigente; luego se consulta la fila para comprobar que corresponde al mismo `jti`, cuenta y digest, y que no fue revocada ni venció en la base. El logout ejecuta una actualización condicional atómica del registro; el llamador confirma la transacción. Después del commit, las validaciones nuevas rechazan el JWT inmediatamente. Solicitudes que ya fueron autorizadas antes del commit concurrente de logout pueden terminar; no se intenta cancelar trabajo en curso.

Este lookup de base de datos por solicitud autenticada es deliberado: evita que un JWT firmado siga autorizando solicitudes posteriores al logout hasta su expiración. Por eso estos JWT no tienen validación completamente sin estado. La consulta debe ser consistente con el commit de logout para ofrecer esta garantía.

Las rutas `POST /v1/auth/register`, `POST /v1/auth/verify-email`, `POST /v1/auth/login`, `POST /v1/auth/login/mfa`, `GET /v1/auth/status` y `POST /v1/auth/logout` conectan los helpers mediante dependencias confiables inyectadas; no leen llaves ni crean conexión a DB al importar el módulo. Registro y verificación requieren sesión DB, Origin exacto, CSRF preauth y rate limiter; el registro además falla cerrado sin screening con lista local y sender. El token de verificación solo se pasa al sender y la base guarda su digest; nunca se devuelve en JSON ni se incluye en errores. El sender se ejecuta dentro de la transacción antes del commit para que un fallo de envío revierta cuenta y token, pero no puede revertirse una entrega si el commit falla después. No hay proveedor real ni lista mantenida configurados por defecto ni ruta de refresh; esto no constituye una afirmación de preparación para producción. El registro conserva el `409` genérico indicado por el contrato actual para conflictos, por lo que el estado HTTP puede revelar una dirección existente.

El JWT y el CSRF usan cookies host-only con prefijo `__Host-`, `HttpOnly`, `Secure`, `Path=/` y sin atributo `Domain`; `SameSite=Lax` es configurable y predeterminado. `SameSite=None` solo se acepta con una allowlist no vacía de orígenes HTTP(S) exactos, y las cookies siguen siendo `Secure`. CORS permite credenciales solo para esa allowlist. Las mutaciones requieren un `Origin` exactamente permitido y `X-CSRF-Token` idéntico al valor del cookie CSRF; el valor CSRF puede volver en JSON para memoria de frontend, pero el JWT nunca aparece en JSON. El estado de sesión no filtra perfil y consulta la fila de revocación.

Si el primer factor encuentra una cuenta con TOTP, el login emite un desafío firmado temporal en cookie HttpOnly, no una sesión. La base guarda solo el digest del desafío y el digest del CSRF que lo emitió. La etapa MFA exige ambos valores originales, revalida la contraseña y elimina el desafío con una operación condicional atómica en la misma transacción que consume el código TOTP y emite la sesión. Si falla la emisión, se revierten consumo y desafío; un segundo uso o un CSRF de otro navegador no autoriza sesión. La migración `0008_mfa_login_challenges` es aditiva. El llamador inyecta las duraciones y la política de límites; aún faltan integración de infraestructura y pruebas PostgreSQL real. No se aplicó ni se probó la migración contra PostgreSQL real en esta tarea.

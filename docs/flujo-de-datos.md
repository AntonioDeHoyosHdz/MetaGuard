# Flujo de datos de MetaGuard

El flujo local implementa carga, análisis, reportes y descarga de un uso con dependencias inyectadas. Cifra archivos temporales en memoria, persiste reportes minimizados en PostgreSQL y ejecuta purgas si hay runtime de archivos y base de datos. Hubo un [ensayo sintético con Docker en WSL](validacion-staging.md#estado-observado); no demuestra el socket Unix nativo con UID separados ni un despliegue de producción.

## Los cinco pasos

| Paso | Recorrido y control | Dato / retención |
|---|---|---|
| 1. Recibir | Navegador → proxy HTTPS local de Vite → API de loopback. Nginx, el saneamiento de cabeceras IP y los límites de borde forman parte del diseño de despliegue, no de la demo. | Solicitud y archivo no confiables. |
| 2. Aceptar | La API valida sesión vigente, Origin/CSRF exactos y límites inyectados; recibe bytes crudos con `Content-Type` allowlist y comprueba el límite configurado mientras consume el stream. No decodifica multipart ni analiza bytes de archivo. Guarda el original mediante `InMemoryTemporaryFileStore` y un runtime inyectado. | Cifrado AES-256-GCM en memoria, ligado a propietario/ID; vencimiento de 10 min según reloj UTC inyectado. La aplicación por defecto no inyecta store ni llave y devuelve `503`. No se calcula SHA-256 en esta ruta. |
| 3. Procesar | La ruta verifica titularidad y usa el cliente privado; FastAPI no ejecuta Docker ni el parser. En Linux, la [configuración documentada](procesamiento-archivos.md#run-the-private-listener-on-linux) conecta cliente y supervisor por socket Unix. | El supervisor envía bytes y MIME al contenedor aislado. La prueba WSL no sustituye la validación de permisos, UID y almacenamiento temporal en staging. |
| 4. Reportar | La API guarda la copia limpia cifrada en memoria y persiste solo la proyección de `ProcessingReport`, propietario, ID y plazos. Si el proveedor está habilitado y `virus_total_consent` es `true`, consulta únicamente SHA-256 del original y la copia limpia, sin bytes ni valores extraídos. El consentimiento es `false` por defecto y el proveedor está desactivado en la demo. | El reporte vence a las 24 h. La respuesta inmediata puede incluir el resultado de reputación; solo la caché independiente conserva el veredicto, estadísticas minimizadas y fecha cuando están disponibles, sin vincularlos al usuario. La cuota persistida es de 4 consultas por 60 segundos y 500 por día UTC. Los fallos del proveedor no invalidan la limpieza; un resultado sin detecciones no demuestra seguridad. |
| 5. Descargar/purgar | Las rutas owner-only emiten un token opaco una sola vez al dueño; se persiste únicamente SHA-256 y el consumo usa una actualización SQL atómica. La ruta descarga bytes de la copia limpia y borra esa copia al consumir el token; el borrado manual de reporte también intenta borrarla. | Token: máximo 10 min desde emisión y no más allá de la ventana de la copia. La copia cifrada deja de estar disponible a los 10 min del análisis. Con un `FileRuntime` configurado, el ciclo de vida de cada API purga entradas vencidas de su propio store; el comando existente sigue purgando filas DB expiradas junto con otros datos. |

## Flujos laterales y reglas

- HIBP, si se habilita, comprueba la contraseña elegida en el registro, el cambio autenticado y el restablecimiento tras comprobar los códigos: envía el prefijo SHA-1 de cinco caracteres y pide padding, con comparación local. La demo usa la lista local y no contacta HIBP. El [restablecimiento](recuperacion-de-cuenta.md#si-olvidaste-tu-contraseña) envía un código distinto del de registro; la base conserva su huella hasta que se invalida o vence. El correo no permite saltar MFA.
- Los reportes no conservan valores de metadatos extraídos. Los tokens de descarga se guardan como digest. El diagnóstico de sistema de protección de contraseñas no se vincula a un usuario. El historial separado de seguridad identifica solo al titular, el tipo permitido, la fecha y la ventana de agrupación. Ambos registros tienen un límite de 30 días; solo tipo y fecha de los eventos de cuenta se muestran al titular. El estado de riesgo usa la huella con llave de la dirección dentro de la cuenta y tiene una retención separada. Si hay un remitente configurado, una cola aparte entrega alertas genéricas sin IP ni contenido de los eventos.
- No registrar cuerpo, contenido extraído, contraseña, hash completo de contraseña, token de sesión/descarga ni llaves. Minimizar también nombre original y errores de parser.
- La purga persistida usa `purge-maintenance`; durante el ciclo de vida de la API también se ejecuta al iniciar y luego cada 60 segundos si están inyectados el runtime de archivos, su store y la base de datos. Un fallo de DB o red se registra sin detalles sensibles y se reintenta en el intervalo siguiente; no detiene la purga del store local. Las sentencias PostgreSQL del worker tienen un timeout de 5 segundos; al apagar la API se cancela el ciclo y se espera a que termine la operación bloqueante en curso, después no se ejecutan nuevos ciclos. Esto no garantiza retención durante caídas ni configura la supervisión de systemd, Docker u otro host. Cada worker puede repetir la purga idempotente de filas DB vencidas; el store cifrado y sus purgas son propios de cada proceso, no portables entre workers. El CLI en otro proceso no puede purgar esos stores. El vencimiento impide el acceso al ciphertext, pero no afirma borrado físico de memoria.

## Qué pasa si falta

Sin este mapa se pierden de vista copias temporales, terceros, claves y plazos; no se puede demostrar minimización ni purga.

## Verificación

Las pruebas sintéticas cubren cifrado, autorización, límites, vencimiento, consumo único y purga de archivos y reportes. El [ensayo HTTPS local](validacion-staging.md#ensayo-local-con-la-interfaz-actual) verificó carga y limpieza de PNG, propiedad, descarga y borrado con PostgreSQL descartable y un adaptador WSL para el procesador. Eso no verifica el IPC nativo con distintos UID, la concurrencia de archivos/reportes en PostgreSQL, la supervisión del host ni la ausencia de restos en tmpfs, logs o base de datos de staging. Tampoco es una captura de egreso de un despliegue con proveedores habilitados.
